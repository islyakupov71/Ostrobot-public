# План работ

Пять этапов. Каждый заканчивается чем-то, что можно показать и потрогать,
а не «продолжением работы над бэкендом». Оценки — для одного разработчика
в паре с Claude Code.

---

## Этап 0. Фундамент — готово

Каркас монорепозитория, схема данных, доменная логика, дизайн-система.

- [x] Монорепо, конфиги, единый контракт типов в `packages/shared`
- [x] Схема БД: пользователи, проекты, задачи, КП, отчёты, правила, напоминания
- [x] Машина состояний задачи с проверкой прав на переход
- [x] Движок правил напоминаний и тихие часы
- [x] Проверка подписи Telegram initData, JWT-сессии
- [x] Двусторонний синк с Google Sheets с защитой от эха
- [x] Дизайн-система и экран «Сегодня»

---

## Этап 1. Живой контур — 3–4 дня

**Цель: сотрудник получает задачу в Telegram и нажимает «Взял».**

- [ ] Миграции применены, сиды заводят администратора и тестовый проект
- [ ] Админ создаёт сотрудника (пока скриптом), сотрудник проходит `/start`
      и подтверждает личность
- [ ] Создание задачи через API, уведомление исполнителю
- [ ] Кнопки «Взял» / «Сдал» меняют статус и пишут историю
- [ ] Воркер разошлёт напоминание за сутки и в момент дедлайна

Здесь выясняется главное: доходят ли сообщения, правильно ли считается время
в часовом поясе сотрудника, не дублируются ли уведомления.

---

## Этап 2. Таблица — 3–4 дня

**Цель: команда работает в таблице как раньше, бот не отстаёт.**

- [ ] Разбор структуры существующей таблицы, настройка маппинга колонок
- [ ] Первичный импорт: задачи из таблицы заводятся в базе
- [ ] Пуш изменений из бота обратно в лист
- [ ] Apps Script и мгновенная реакция на правки
- [ ] Отчёт о конфликтах и о неразобранных значениях

Самый рискованный этап: реальная таблица всегда устроена не так, как ожидалось.
Заложено время на подгон маппинга под то, что есть.

---

## Этап 3. Mini App — 5–7 дней

**Цель: всё, что неудобно делать кнопками в чате.**

- [ ] Вход по initData, обновление сессии
- [ ] Экраны: Сегодня, Мои задачи, Дедлайны, карточка задачи
- [ ] Смена статуса, описание блокировки, комментарии
- [ ] Экран КП: отметка отправки и подтверждение получения
- [ ] Экраны руководителя: Команда, Статус проектов
- [ ] Пустые состояния, скелетоны, обработка потери связи

---

## Этап 4. Контроль и отчётность — 4–5 дней

**Цель: то, ради чего бот заводился — никто ничего не забывает.**

- [ ] Шаблоны регулярной отчётности, генерация периодов
- [ ] Контроль заполнения статус-таблицы
- [ ] Эскалации руководителю при отсутствии реакции
- [ ] Утренняя сводка: просрочки, задачи без реакции, блокировки
- [ ] Настройка правил уведомлений администратором

---

## Этап 5. Прод — 2–3 дня

- [ ] Сервер, домен, TLS, webhook
- [ ] CI: сборка образов и деплой по пушу в `main`
- [ ] Резервное копирование базы по расписанию
- [ ] Системный журнал и экран администратора
- [ ] Обучение команды: что нажимать и что произойдёт

---

## Что стоит решить по ходу

**Структура существующей таблицы.** Маппинг колонок написан под гипотезу.
Как только появится доступ к реальному листу, он почти наверняка изменится —
это нормально и заложено в оценку этапа 2.

**Тихие часы против срочности.** Сейчас просрочка проходит сквозь тишину,
а рутина копится до утра. После недели работы станет понятно, не слишком ли
это шумно — правила меняются данными, без правок кода.

**Приёмка работы.** Заложено, что «Выполнено» ставит постановщик, а исполнитель
может только «Сдал». Это дисциплинирует, но добавляет шаг. Если команде окажется
тесно — переход `submitted → done` открывается исполнителю одной строкой
в `packages/core/src/task-status.ts`.
